## 判断与责任

反复失败集中在模型备忘录的生成和验收层。既有 PDF 解析、冻结计算、版本保存与回滚已有普通回归证据，但真实备忘录尚未达到稳定演示标准。

此前逐次追加模型指令、每次用一个新真实输出检查的做法，能定位单个问题，却没有建立固定版本下的稳定性证据。Codex 对指令、输出结构、校验和测试范围的整体设计不够完整，应更早合并检查这些要求，而不是持续以局部追加和再次运行推进。用户选择了正确的分支和提交。

程序正确阻断不合格输出有价值，但“会拦错”和“能持续产出可用草稿”是不同的能力。普通测试通过不能代替后者，技术完成也不能代替会计、估值或研究内容复核。

## 代码与任务设计中的薄弱处

| 位置 | 当前实际行为 | 影响 |
| --- | --- | --- |
| 模型指令 | 五个指令块组合，共 2,227 字符；要求事实解释、权衡、替代机制、补证问题、引用、格式及多项边界同时满足 | 局部追加保留了规则，却增加了重复和协调负担；这是需验证的设计判断，不是已证明的 token 因果关系 |
| 输出结构 | 已使用 `text.format: json_schema`，并非没有结构化输出；但字段长度、条数及方向组合约束未完整写入 Schema | 返回合法字段仍可能不满足后续程序的栏目要求，结构化输出也不能防止输出预算截断 |
| 长度与条数 | Prompt 为每段至多三百汉字、替代解释一至两条；程序安全上限为八百字符，各数组一至三条；Schema 没有相应长度或条数限制 | 生成目标与阻断上限分散，应明确哪些是目标、哪些是硬限制，并统一实现 |
| 反证栏目 | 导出标签为“反证与限制”，但程序要求每条都引用方向为反证的事实 | 独立限制说明在研究上有意义，却不一定满足此栏目规则；名称和逐段要求应对齐 |
| 普通测试 | 提供方使用注入的传输替身，浏览器模型环节使用预设返回 | 能证明代码边界和交互，无法测出真实推理用量、表达波动和引用是否蕴含每个判断 |
| 内容输入 | 当前只是选定的已审核财务事实及冻结规则；没有模型可用的报告全文或经营原因明细 | 无法仅靠追加指令补足未知会计性质、原因与持续性；这些仍需材料和人工专业判断 |

程序计算、引用校验和专业关卡仍需保留。改用其他提供方、关闭思考模式、提高输出上限或自动重试都不是已证明有效的解决方案；本轮不擅自采取。

AI 继续承担支持与反证的权衡、待验证解释及补证问题。确定性财务计算、专业关卡、人工最终判断和研究版本留痕保持原定义。此次仍为 S-05 / C-04 验证；S-06 仅做原有普通回归，S-07 继续不读、不测。跨公司能力仍为独立阶段。

实施顺序与验收条件：

1. 先在 GitHub 分支完成统一约定、精简指令、结构与文案对齐，以及按版本保留历史记录；以原始要求清单逐项核对没有丢失事实/假设区分、反证保留、逐段引用、专业待复核和人工决策边界。
2. 离线检查应包含合法完整输出、方向错误、缺失或未知引用、错误条数/长度、重复 JSON 字段、截断、旧记录可读、阻断后不改快照。沿用已有合成文案，不把真实历史原文转成仓库标准答案；普通 CI 仍检查构建与浏览器流程。
3. 通过后由所有者手动启动一次固定版本验证批次。最多三个样本、每个一次请求、逐个执行。出现接口、截断或结构阻断则停止余下样本并保留所有已发生调用；没有自动重试，也不追加第四次“直到成功”。
4. 每次最多 6,000 输出 token，整个批次最多 18,000 输出 token，另计实际输入用量；这只是调用用量上限，不是人民币固定费用。不会自动增加预算、更换模型或关闭思考模式。
5. 全部完整输出分别审阅证据、归因、会计前提与研究问题，并报告每个样本的成败、token、时长和内容问题。若三份均通过，只记为该固定案例/版本的初步重复验收通过，不能称产品准确率或长期稳定性已获证明。
6. 达标后提交整链演示的收尾结果与下一阶段建议；未达标则停止本轮调用，带具体失败和成本回来重新决策。预算调整、模式对照或输入扩展届时分别提案，不继续无限追加指令。
