# 问题入口真实验收 V0.1

日期：2026-09-20。状态：**工具已准备；新问题 Prompt 的真实运行与人工内容结论待完成**。本批次来自用户对非 UI 工作“以上全部同意”的授权。与历史 Memo run-10 分开留档。

## 固定实验设计

输入为已登记官方 S-05 PDF，经普通浏览器流程解析/核对保存的快照；原 PDF SHA-256 为 `88d2ab7c603a94b7e0943ef07e219235ee59b9048e1dfa8e38bd6ebac99b6d03`。CI 中证据接受动作是自动交互验证，不能冒称真实人类审核身份。

三个固定问题写在 `apps/web/scripts/run-question-batch.mjs`：Q-LIVE-01 变化解释、Q-LIVE-02 证据核验、Q-LIVE-03 决策影响。每题规划一次、确认执行一次，**合计至多 6 次请求**；DeepSeek V4 Pro / low / 每次最多 6,000 输出 token、150 秒。36,000 是总输出上限，不是总 token、费用报价或实际耗用；输入及失败请求可能另计费。收到用量才累计已知用量，缺响应记 unknown。

任何网络、模型、截断、结构、意图、证据绑定或归档失败立即停止剩余请求。无自动重试、不执行第四题、不修补模型原文、不把失败删掉换一批。三题是三个不同意图的验收，**不是重复采样的稳定性或统计显著性证明**。

## 执行入口

1. 确认普通 Web CI 在指定提交通过；工作区、工作流与依赖可查。
2. 在 GitHub Actions 选择 `Live question acceptance (manual, at most six requests)`。仅 `workflow_dispatch`；push / PR 不调用模型。
3. 选分支并填完整 40 位 `expected_commit`，授权标记 `question-acceptance-2026-09-20`。执行的 SHA 不符或 attempt 不是 1，使用密钥前终止。已有一次实际执行后不要另建新 dispatch 规避失败停止。
4. 工作流普通检查先行，真实步骤才使用仓库现有 `DEEPSEEK_API_KEY`。不查看或复制密钥。同一批证据输出到 `question-live-<runId>-attempt-1`。

工具先写请求预留记录，再请求；逐次保留原始输出、Prompt/请求/响应摘要、事件、失败和用量。临时访问码及签名执行 ticket 不进验收包。若请求失联，预留记录仍保留，不能推断没有费用。技术成功只写 `technical-completed-awaiting-content-review`。

## 预先确定的验收口径

| 层级 | 条件 | 失败如何记 |
| --- | --- | --- |
| 技术 | 真实 provider/model、准确意图/期间、单次调用、原始输出和事件完整、合同绑定、冻结证据与计算重放一致 | stop；缺依赖/网络是执行失败，不是研究假设被否定 |
| 内容：问题相关 | 三个意图各回答自己的问题，不用同一套空泛段落替代 | 逐题说明不符之处 |
| 内容：事实 / 引用 | 正文与结构化数字一致；引用覆盖事实及比较双方；能回到实际页码 | 记录具体段落和证据 ID |
| 内容：推论 | 分开本期口径桥、同比变化和原因；归因无证据则明确待核验 | 不凭桥闭合证明经营改善 |
| 内容：边界 | 反证保留；A-03 待核验；K-07 clear 不代表风险消失；不输出正式建议 | 不以修改规则使输出通过 |
| 专业 | EG-01 / EG-02 仍待真实专家的有限范围意见 | 不由助手代签 |

内容审阅另存追加记录，绑定 runId、commitSha、snapshotSha256、answerSha256、原文段落与结论。助手可以做技术/内容初审；用户内容接受及专家认可分别记录，不自动继承。每题只记“可接受 / 需修订 / 阻断 / 未运行”及理由，不虚构总分。
