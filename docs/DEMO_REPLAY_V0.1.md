## 一次生成完整离线包

1. 下载并解压[既有归档](https://github.com/yivenwang/financial-research-decision-chain/actions/runs/34342481369/artifacts/10100481118)。其结构为一个批次 manifest 和 `sample-01`、`sample-02`、`sample-03`，共 28 个文件。GitHub 下载是否要求登录以实际权限为准，归档有保留期限。
2. 在仓库根目录，用 Node.js 22.16.0 运行下列命令；替换两个目录，输出目录必须尚不存在，且父目录已存在。

```bash
node --experimental-strip-types apps/web/scripts/prepare-demo-replay.mjs --archive-dir /absolute/path/to/extracted-run-10 --out /absolute/path/to/new-replay-folder
```

3. 双击输出目录的 `index.html`。可查看全部三份原稿、逐段建议、引用和原界面截图。页面只在展开证据时改变阅读状态，没有生成、导入或接受按钮。

工具先核对[28 个文件的注册长度与字节 SHA-256](demo/run-10-archive-manifest.json)，再从三个研究快照重新执行既有引擎并核对模型 context、原始 JSON 映射、原审核、原 Markdown、原快照及建议绑定。任何文件缺失、变动、多出文件或目录/符号链接异常都会阻断生成；不会修补原文后继续。原 ZIP 摘要见注册文件，工具核对的是解压后的每一个注册文件。

输出的 `original/` 逐字节保留全部 28 个原文件；`replay-data.json` 包括三组独立 snapshot、run、reviews、回滚及人工建议。`sample-01-review.md` 至 `sample-03-review.md` 便于逐段核对；`verification.json` 记录核验结果与产物摘要。输出目录已存在时拒绝覆盖，写入失败时保留部分结果供诊断，解决后选新目录重做。

## 数据怎样给 UI 使用

`replay-data.json` 是离线核对数据格式，不是产品已接受台账。每个 `samples[i]` 包含：

| 字段 | 用途 |
| --- | --- |
| `original.snapshot` | 真实归档研究版本、证据、冻结计算与专业关卡 |
| `original.run` | 原始 DeepSeek 调用、六段文案、引用、Prompt 与用量 |
| `original.reviews` | 原自动化审核事件，逐字保留；不能改称真实用户签署 |
| `original.afterRollback` | 原归档中的追加回滚结果 |
| `proposal` | 对应这份原调用的六段建议、每段处置理由、来源/内容摘要；离线包保留生成时的待确认状态，后续决定由独立记录绑定 |

三个独立样本都使用 V-02 名称，但快照摘要不同；不能把它们合并进同一个浏览器版本库。当前产品没有原生归档导入入口，本轮没有添加导入脚本或修改存储。开发者在后续 UI 任务中可用这些数据核对组件字段；实际交互仍通过产品及已有合成浏览器回归验收。

## 演示讲述与内容确认

先展示一份材料中的支持和反证为何同时存在，再展示程序负责的本期利润桥、会计假设待复核与继续研究的动作。随后用样本 01 的反证段解释“为什么需要人工修改”，查看修订建议与来源；同时说明整批三份结果，提供其余两份供核对，不只选最好的一份。

正式拍摄人工修订时，操作者按已确认建议在产品编辑入口输入正文及修改理由，再核对并确认准确版本。所有者决定已记录在 GitHub，但没有伪装成三个不同快照已经写入同一浏览器台账。使用新生成的真实草稿进行彩排时，需另行安排已批准的调用额度；历史回放不消耗新额度。

全流程时间仍按[演示脚本](COMPETITION_DEMO_SCRIPT_V0.1.md)预排，尚未声称完成计时预演或正式视频。技术正确、内容确认、专业复核和视觉验收分别记录。
